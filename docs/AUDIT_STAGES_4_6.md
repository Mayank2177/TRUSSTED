# Stage 4–6 implementation audit

Status: research prototype code review and local regression verification. This document describes the current implementation in `priyansh/pipeline-4-6`; it is not a production security certification.

## Stage 4: perturbation and stability

- `StabilityConfig` rejects `shuffle_count < 1`.
- Persuasion stripping removes only explicitly typed `marketing` and `review` prose. If a removed block carries structured fields, Stage 4 copies those fields into a structured block; fact, structured, and unclassified blocks remain. Source observations are immutable.
- Baseline and transformed observations use the same versioned `warrant-observation-content-v1` SHA-256 of typed blocks, including kind, text, structured data, and source order. Object keys are sorted, JSON is compact, Unicode is UTF-8, and non-finite values are excluded by strict scalar types. The upstream raw/source hash is retained separately as `source_content_hash`.
- A shuffle uses the existing `seed + index` seed plan. Identity permutations are redrawn using the same seeded random stream until a changed order is produced. With one candidate, a changed order is impossible and is reported as unchanged.
- Each `PerturbationOutcome` reports `changed_input`. `StabilityReport.changed_count` and `shuffle_changed_count` count actual changed inputs, including a changed input whose extraction/ranking callback subsequently fails. They do not count a no-op transformation.
- Reports distinguish `completed`, `failed`, and intentional `skipped`. `StabilityRunner.skipped(run_id, reason)` emits `stable=False`, zero planned/failed counts, no outcomes, and an explicit reason. Missing/invalid baseline evidence is `failed`; callback timeout is a failed outcome with `TIMEOUT`.
- `stable` remains a strict winner-equality result: the baseline winner must exist, every planned run must succeed, and every perturbed winner must match the baseline. A shuffle that cannot change a one-candidate input does not itself make the report unstable. Stage 5's `evaluate_same_run` additionally requires at least one successful shuffle that actually changed ordering before accepting stability evidence for ALLOW.
- Baseline and perturbed extraction facts are runtime-validated for required types, candidate membership, seller, SKU/GTIN shapes, minor-unit prices/charges, currency, specs, and source spans. A winner must have a unique fact and nonempty SKU; a missing SKU does not fall back to GTIN. When the same candidate wins, seller/SKU/GTIN/price/currency/shipping/charges/specifications must match the baseline or that outcome fails with `WINNER_FACT_DRIFT`.
- Sub-run IDs are generated and checked before callbacks: each must be nonempty, unique, and different from the parent run ID. Failure prevents callback execution.
- Callbacks receive a timeout contract but must enforce it themselves. There is no hard process isolation or forced termination of synchronous callbacks.

**Persistence adapter:** `warrant.integrity.persistence` now calls Ayush's `save_product_facts`, `save_ranking`, `save_stability_report`, and `record_stage_state` functions. It retains extraction-specific fact IDs and accepts only an explicit mapping that matches each fact's seller/SKU. Ranking and winner-count references are resolved through those mappings and checked by the shared same-run repositories. Skip/error/timeout are recorded as distinct `StageState` values; the current schema has no report row for failed outcomes, so those reports retain only the stage reason there. Mayank's current flattened content and content-derived IDs still do not satisfy the source mapping contract by themselves.

The implementation contains no Stage 1–3 cache. Upstream extraction caching must incorporate transformed `content_hash` (or the transformed canonical content) rather than keying only on candidate ID. Full hash and report contract details are in `docs/PIPELINE_CONTRACTS.md`.

## Stage 5: deterministic authorization

`decide` is a pure deterministic function and contains no LLM or probabilistic call. It applies the documented priority: high-severity fact conflict blocks; disallowed winner or hard-constraint violation blocks; instability, qualifying missing reference, upstream failure, or missing/invalid evidence steps up; otherwise it allows. Block reasons dominate step-up reasons. Invalid typed conflict/failure evidence is not silently accepted. `BLOCK` is the documented outcome name in the PRD, architecture, and model; no separate `DENY` value is introduced.

`policy_version` emitted on a decision includes a deterministic SHA-256 fingerprint of the configured currency thresholds. `PolicyInput` carries a distinct `winner_fact_id`; missing fact identity prevents ALLOW. Decisions contain a deterministic approval hash bound to run, winning fact, result, reasons, policy version, amount/currency, and supplied evaluator evidence. `evaluate_same_run` is the typed assembly boundary: it checks same-run ownership and winner identity, derives hard constraints from the winner fact and intent, and rejects stability reports with missing, skipped, failed, incomplete, wrong-winner, threshold-invalid, or no-meaningful-shuffle evidence. These DTOs are not cryptographic attestations; an API must assemble them from trusted outputs. Mayank's separate policy implementation remains an integration-owner decision. MEDIUM conflicts do not independently block or step up under the current evaluator.

The existing policy regression suite covers deterministic repeatability, conflict severity, block priority, missing/invalid evidence, missing thresholds, stability, upstream failure, and threshold boundaries. No policy-source derivation redesign was made. Stage 3 remains responsible for ranking and hard-constraint evidence, while the policy consumes the explicit evidence in `PolicyInput`.

## Stage 6: credential and mock gateway

- The public `issue_credential` function checks ALLOW and amount/currency, then fails closed because no contract proves that the supplied cart represents the selected Stage 3 winner and seller. No token or credential row is created through this function until that proof is available. Ledger checks are tested directly with test-only signed fixtures; those tests do not claim the public issuer creates credentials.
- Against the supplied Ayush run schema, issuance also requires an existing run in `running` or `completed` state; `error` and `timeout` runs fail closed.
- Runtime credential persistence is `SharedCredentialLedger`, an adapter around Ayush's canonical repositories and `transaction()` helper; the old raw-SQL test adapter is confined to `tests/support`.
- Decision and credential writes occur in one transaction. `store_credential` checks same-run ALLOW, amount/currency, run lifecycle, expiry, and the persisted approval hash. Migration `0009_one_credential_per_run` supplies database-level uniqueness; application attempts also translate duplicate repository writes to `CredentialAlreadyIssued`.
- JWT uses EdDSA, the configured key ID, issuer, audience, version, run ID, cart hash, merchant, amount, currency, expiry, issue time, and nonce. The gateway pins the algorithm, rejects malformed headers and required-claim/type failures, checks expiry against its injected clock, requires a caller-supplied expected run ID matching the signed claim, and compares the submitted cart's merchant, amount, currency, and canonical cart hash before consulting persistence. The ledger independently checks the run ID in its redemption transaction.
- Redemption validates signature, required claims, run, cart hash, merchant, amount, currency, expiry, and approval hash before opening a fresh transaction. The shared repository performs the nonce/expiry/approval-hash conditional UPDATE as its first database operation. Gateway acceptance is returned only after commit; false or database errors reject.
- The gateway is mock-only. No PayPal adapter, production credential, external payment call, or capture flow exists.
- The gateway clock is constructor-injected; an HTTP request cannot supply a verification time. On POSIX, key generation uses exclusive private-file creation with mode `0600`; on Windows it relies on inherited directory ACL and does not set a per-file DACL.
- `SharedCredentialLedger.create_after_allow` and repository `store_credential` are persistence APIs. They do not establish cart-to-winner identity and must not be exposed as authorization or issuance endpoints. `persist_decision` and `create_after_allow` both write the run's decision; calling both for the same run causes duplicate-decision failure.

### Authorization binding gaps requiring a contract decision

1. Decision winner provenance is now persisted in `winner_fact_id`; migration `0008_decision_product_provenance` backfills historical ALLOW winners only when exactly one base ranking proves the identity, otherwise it aborts without rewriting data. The database has no approved stable cart `item_id` or mapping for seller, SKU, quantity, unit price, and shipping/tax/discount totals. Public issuance remains disabled pending that owner contract.
2. Run binding is implemented: the signed token contains `run_id`, gateway verification requires the API caller's expected run ID, and redemption compares it with the persisted row within the transaction.

Ayush's canonical package is included from the supplied archive; the runtime adapter invokes its repositories only. Redemption compares the signature-verified authorization values to the stored row in one conditional UPDATE. The migration-backed tests cover this predicate and the one-run constraint and passed with the pinned dependencies.

Persisted ranking labels are restricted to `none`, `strip_persuasion`, and zero-based `shuffle_i`. Stage 4 adapter inputs map fresh perturbation fact IDs to parent-run facts by an explicit seller/SKU pair; no hostname/fact-ID inference is used. Successful reports preserve versioned report details, callback IDs, seeds, winner mapping, and change counts in the `flips` JSON. The shared schema has no failed-report payload, so failed/skipped/timed-out reports persist a stage state and reason only.

## Supplied teammate archive compatibility

The archives are code/specification artifacts. Any planning text inside them does not authorize changes to other owners' components or override the user's scope. In particular, Mayank's archive contains a duplicate `trussted.db` implementation and a PayPal integration; Ayush's `warrant.db` package is the database-owner implementation, and the PayPal code is not adopted.

Migrations `0008_decision_product_provenance` and `0009_one_credential_per_run` are forward-only additions. The first preserves legacy rows, safely backfills winners only from unique base rankings, and prevents new ALLOW rows without a winner. The second checks duplicate run credentials before adding uniqueness and reports duplicates without deleting them. Runtime decisions/credentials use Ayush's `DecisionInput`, `CredentialInput`, and repository functions. The approval-hash field remains nullable for legacy credentials/decisions; legacy ALLOW rows without it cannot issue a new credential.

Stage 4 is not yet directly wireable to Mayank's current output. Mayank's `Observation` does not retain the sanitized text or typed content blocks required for persuasion stripping; its sanitizer produces flattened text without marketing/review classification. Its `observation_id` hashes URL plus page bytes, and `fact_id` incorporates that content-derived ID and extraction index, so those IDs change across perturbation content. Stage 4 needs classified retained source segments and a stable candidate identity across re-extraction. Adding a classifier or silently treating all page text as non-persuasive would violate the Stage 4 contract.

Mayank's `ProductFact` carries a per-observation fact ID, seller/merchant, optional SKU, and `Money`; Ayush persists per-extraction IDs, seller, required SKU, and base ranking winner. The adapter requires real seller/SKU evidence and keeps fresh fact IDs. Missing SKU is rejected. Decision winner provenance is added here. The cart's `product_id`/SKU/quantity and shipping/charge mapping to those rows remains undefined, so exact winner/cart binding is unresolved. Do not synthesize product identity.

The dashboard archive uses the expected `ALLOW | STEP_UP | BLOCK` union and string reason arrays, but its API client and screens contain hardcoded sample benchmark metrics and a fallback receipt verifier that only checks nonempty strings. Those values cannot be represented as verified benchmark or receipt results. Dashboard changes belong to its owner; the API does not yet exist in this branch. Mayank's `docs/New Text Document.txt` proposes Channel3, PayPal sandbox payment, and Render hosting; those are proposals inside an artifact, not user authorization. No such integration is adopted here.

## Verification and limits

On the exact correction-pass source revision, the full suite passed **356 tests** and the focused Stage 4–6 suite passed **173 tests**. Ruff check passed; Ruff format check passed with **100 files already formatted**; strict mypy passed with no issues in **62 source files**. The full suite includes the real migration-backed tests. Environment: CPython 3.12.10, SQLAlchemy 2.0.55, Alembic 1.20.1, Pydantic 2.14.1, pytest 9.1.1, PyJWT 2.15.1, Ruff 0.17.2, and mypy 2.4.0. No dependency pins were changed.

The tests cover the stated local behaviors; they do not establish production security or a composed API workflow. Mayank's returned output lacks typed visible-content blocks and authoritative seller identity. Deepika's supplied archive has no backend routes or request models. Exact winner-to-cart identity remains unavailable, so `issue_credential` stays disabled. `create_after_allow` and `store_credential` are persistence APIs only and must not be exposed as authorization or issuance endpoints. `persist_decision` followed by `create_after_allow` duplicates the decision write for the same run. See the current integration requirements in `docs/FINAL_IMPLEMENTATION_AND_SECURITY_AUDIT.md`.
